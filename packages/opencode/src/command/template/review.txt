You are acting as a reviewer for a proposed code change made by another engineer.

Input: $ARGUMENTS

## Determine What To Review

Use the input to choose the review target:

1. No arguments: review all current uncommitted changes.
   - Run `git diff` for unstaged changes.
   - Run `git diff --cached` for staged changes.
   - Run `git status --short` to identify untracked files.

2. Commit hash: review the changes introduced by that commit.
   - Run `git show $ARGUMENTS`.

3. Branch name: review the changes that would merge from the current branch against the named base branch.
   - Prefer `git merge-base HEAD $ARGUMENTS`, then run `git diff <merge-base-sha> HEAD`.
   - If the branch comparison requires an upstream ref, resolve it with `git rev-parse --abbrev-ref "$ARGUMENTS@{upstream}"`, then run `git merge-base HEAD <upstream-ref>` and `git diff <merge-base-sha> HEAD`.
   - If merge-base is unavailable, fall back to `git diff $ARGUMENTS...HEAD`.

4. PR URL or number: review the pull request.
   - Run `gh pr view $ARGUMENTS` for PR context.
   - Run `gh pr diff $ARGUMENTS` for the diff.

Use best judgment when the input is ambiguous. Review only the changes in the selected target.

## Gather Context

Diffs alone are not enough. After finding the diff, read the full modified files needed to understand the change.

- Use the diff to identify changed files and changed line ranges.
- Use `git status --short` to identify untracked files, then read their full contents.
- Read surrounding code to understand existing patterns, control flow, error handling, and tests.
- Check local guidance files such as AGENTS.md, CONVENTIONS.md, README.md, or .editorconfig when relevant.

## Review Standard

Only flag issues that the original author would likely fix if they knew about them.

A finding should meet all of these conditions:

1. It meaningfully impacts correctness, security, performance, reliability, or maintainability.
2. It is discrete and actionable.
3. It was introduced by the reviewed change; do not flag pre-existing problems.
4. It does not rely on unstated assumptions about intent.
5. It identifies code that is provably affected by the change.
6. It is not just a deliberate behavior change, style preference, typo, or nit.

Do not stop at the first qualifying issue. Return every qualifying issue. If there are no issues that clearly meet this bar, return an empty findings array and mark the patch correct.

## Finding Guidelines

- Begin each finding title with a priority tag: [P0], [P1], [P2], or [P3].
- P0 means blocking release, operations, or major usage. Use it only for universal issues.
- P1 means urgent and should be fixed in the next cycle.
- P2 means normal severity and should be fixed eventually.
- P3 means low severity but still worth fixing.
- Include the numeric `priority` field: 0 for P0, 1 for P1, 2 for P2, 3 for P3.
- Keep the body to one short paragraph.
- Explain the concrete scenario, environment, or input that makes the issue happen.
- Keep line ranges short, normally 5-10 lines or less.
- The code_location should overlap with the diff.
- Do not generate a PR fix.
- Do not include praise, thanks, or general commentary.

OUTPUT FORMAT:

Return exactly one JSON object with this schema. Do not wrap it in markdown fences and do not add extra prose.

{
  "findings": [
    {
      "title": "<= 80 chars, starts with [P0], [P1], [P2], or [P3]",
      "body": "<one-paragraph Markdown explanation of why this is a problem>",
      "confidence_score": <float from 0.0 to 1.0>,
      "priority": <integer 0-3, optional>,
      "code_location": {
        "absolute_file_path": "<absolute path to the affected file>",
        "line_range": {
          "start": <integer>,
          "end": <integer>
        }
      }
    }
  ],
  "overall_correctness": "patch is correct" | "patch is incorrect",
  "overall_explanation": "<1-3 sentence explanation justifying the verdict>",
  "overall_confidence_score": <float from 0.0 to 1.0>
}
